# 结构自演化与历史重解释：独立后续设计

状态：设计边界已冻结；没有接入运行时、scheduler、历史迁移器或通用学习框架。

## 结构自演化

结构自演化只处理 schema、索引、模块连接和可观测性结构的候选变更。它不能直接修改 Persona、Affect、Relationship、Identity claim、工具权限、回复参与策略或历史记录。

每个结构候选必须包含：候选 ID、现有 schema 版本、目标 schema 版本、产生原因、受影响 owner、兼容读取方案、离线迁移计划、回滚计划、验证结果和维护者批准记录。候选默认 `PENDING`；只有维护者显式批准后才能进入隔离实例验证。生产发布继续走普通代码审查、备份和部署流程，不允许模型在运行中修改模块结构。

建议调用链：观测指标或人工问题单 → 生成结构候选 → 静态兼容检查 → 虚构数据迁移预览 → 人工批准 → 隔离实例部署 → 回滚演练 → 独立生产发布授权。任何阶段缺少 owner、schema 或回滚证据时停止该候选。

## 历史重解释

历史重解释只生成新的派生解释记录，原始消息、P2r0 facts、ReviewEvidence、Episode 和旧解释保持不可变。新解释必须引用精确来源 ID、解释器版本、规则版本和生成时间；不能用昵称、文本相似度、时间最近或模型猜测补足身份和回复链。

历史重解释分成两个动作：

1. 只读预览：允许对明确授权的 ID 范围生成派生解释和差异，不写回权威存储。
2. 发布派生解释：需要逐条清单、前置版本、字段前后值、证据、备份位置、恢复验证和明确批次授权。发布只新增版本化解释，不覆盖原始事实。

撤销通过将派生解释标记为 `REVOKED` 完成；冲突标记为 `CONFLICTED`，不采用最新或多数自动胜出。旧迁移器不能作为重解释入口，也不会在启动或 scheduler 中自动运行。

## 与现有能力的关系

- R02/L28 只负责一条 `response_style_preference:v1` 的条件维护，不是历史重解释引擎。
- R04 只保存无正文的精确反馈观察和失效状态，不从旧 archive 补造反馈。
- R07、R08、R10、R11 各自保留既有 owner，不向本设计移交写权限。
- Persona revision 继续人工批准；结构候选不能调用 `approve_revision()`。
- 本设计没有通用奖励、自动偏好归纳、自动 Persona 修改或全量历史迁移。
